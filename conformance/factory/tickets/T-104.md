# T-104 — operator can retry a dead job

State: In progress
Branch: ticket/T-104-retry-dead-job
Risk class: medium (touches the worker/queue lifecycle, but no external actions)

## Description

A job that fails 3 times goes to the dead-letter and stays there forever. Operators need a second chance after fixing the underlying cause: an explicit, auditable retry.

- `POST /api/jobs/:id/retry` re-queues a **dead** job: it becomes pending again with a fresh attempt budget (3 more attempts), and the worker picks it up on its normal tick.
- The job record keeps its history: total attempts accumulate across retries, and the record shows it was retried (planner freezes the representation, e.g. a retry count).
- Retrying a job that is not dead is refused with a clear status code and no change (planner freezes which code).
- Everything persists: a retry survives a kill/restart, and a re-queued job that keeps failing goes dead again after its 3 new attempts.

## Acceptance criteria (planner freezes the exact contract)

1. A dead job, retried → pending again; a job whose cause is fixed (payload stops failing) completes and produces its proposed action as normal.
2. A dead job, retried, still failing → dead again after exactly 3 new attempts, with cumulative attempts visible on the record.
3. Retry of a non-dead job (pending or done) → refused with the frozen status code, record unchanged.
4. Kill the server right after a retry is accepted; on restart the re-queued job is processed (crash recovery holds).

## Frozen contract

### `POST /api/jobs/:id/retry`

`:id` is the job's `id` field exactly as it appears in `/api/state` (e.g. `job-e4`), matched against `state.jobs`, route regex `^\/api\/jobs\/([^/]+)\/retry$`. No request body is read or required.

- Unknown `:id` → `404 { "ok": false, "error": "no such job" }`, no state change.
- Job exists but `status !== "dead"` (i.e. `pending` or `done`) → `409 { "ok": false, "error": "only dead jobs can be retried (status: <current-status>)" }` — `<current-status>` is the literal current value of `job.status` (`"pending"` or `"done"`), record unchanged (no field, including `lastError`, is touched; no `persist()` call happens on this branch).
- Job exists and `status === "dead"` → accepted:
  - `job.status` → `"pending"`
  - `job.attemptsSinceRetry` → reset to `0`
  - `job.retries` → incremented by `1`
  - `job.attempts` and `job.lastError` are **not** modified by the retry call itself (the next worker tick updates them exactly as it does today)
  - state is persisted atomically before the response is sent
  - Response: `200 { "ok": true, "status": "pending", "retries": <job.retries after increment> }`

### `GET /api/state` — `jobs[]` shape (additive, present on every job from creation, not just retried ones)

Every job object gains two new keys, initialized at creation in `acceptEvent` alongside the existing `attempts: 0, lastError: null`:

```json
{ "id": "job-e1", "eventId": "e1", "status": "pending", "attempts": 0, "lastError": null, "retries": 0, "attemptsSinceRetry": 0 }
```

- `retries` (number): count of times `POST /api/jobs/:id/retry` has been accepted for this job. `0` until first retry, then increments by exactly `1` per accepted retry call. This is "the record shows it was retried" representation the ticket description asks the planner to freeze.
- `attemptsSinceRetry` (number): attempts made since job creation, or since the most recent accepted retry, whichever is later. Incremented by `1` in the same worker tick that increments `attempts` (so it always equals `attempts` until the first retry, after which it runs ahead of `attempts` by the reset amount). This is the internal counter that drives the "3 more attempts" budget below — it is not itself a public promise beyond what AC1–AC4 require, but it is real state and will appear verbatim in `/api/state`, so the test-author may assert on it directly.
- `attempts` is unchanged in meaning: **cumulative total attempts across the job's entire lifetime, including all retries** — never reset. This is the "cumulative attempts visible on the record" the ticket asks for.

### Worker/dead-letter logic change (in `processJob`)

Today: `if (job.attempts <= failTimes) { ...; if (job.attempts >= MAX_ATTEMPTS) job.status = "dead"; }`.

New: increment both `job.attempts` and `job.attemptsSinceRetry` on every attempt; the dead-letter check moves from `job.attempts >= MAX_ATTEMPTS` to `job.attemptsSinceRetry >= MAX_ATTEMPTS` (`MAX_ATTEMPTS` stays `3`, unchanged, reused as-is). The failure-vs-success check itself (`job.attempts <= failTimes`) stays keyed on cumulative `attempts`, not the reset counter — this is what makes "payload stops failing" (AC1) fall out for free: once cumulative `attempts` exceeds the event's fixed `failTimes`, every future attempt (retried or not) succeeds, without any payload mutation. For a job never retried, `attemptsSinceRetry === attempts` at all times, so pre-existing dead-lettering behavior (dead at exactly 3 cumulative attempts) is bit-for-bit unchanged.

`workerTick` itself is unchanged: it still picks the first `status === "pending"` job in array order per tick, which already covers "the worker picks it up on its normal tick" for a re-queued job.

If this contract proves wrong during build or test-authoring, the ticket goes back to Ready for re-planning as a new version — do not silently change the shape.

- `tests/conformance.test.js` tests `"3. transient failure..."` and `"4. permanent failure..."` assert individual fields (`job.status`, `job.attempts`, `job.lastError` via `assert.strictEqual`/`assert.match`), never a full-object `deepStrictEqual` on a job. Both tests exercise jobs that are never retried, so `attemptsSinceRetry === attempts` throughout and the dead-letter trigger point (3 cumulative attempts) is unchanged for them. **Not affected, no edits needed.**
- `tests/reject-reason.test.js` builds exact expected **approval** objects (`expectedApproval`) via `deepStrictEqual`, never touches `jobs[]`. Retry has no effect on approvals. **Not affected, no edits needed.**
- No test file anywhere does `assert.deepStrictEqual` (or an exact `JSON.stringify`/full-body match) against an individual job object or against the full `jobs[]` array in `/api/state`.

**Conclusion: zero existing tests require amendment.** `tests/retry-dead.test.js` is a purely additive new file; the test-author does not need to touch any pre-existing test file for this ticket.
