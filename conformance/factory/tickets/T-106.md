# T-106 — add a backend-readiness operator check

State: Building
Initiative: I-002
Priority: low
Risk class: low
External: no

## Description

Add `scripts/adapters/contract-test.sh --readiness` as the operator's
ticket-independent check of all four kit-owned backend adapters. It reports
each adapter's provider family and probe result, then reports whether the
production/OpenAI and checking/Anthropic role groups each have a safe startup
route. It must invoke only the existing non-task probes: it never accepts or
submits role/task content.

This is the operator-facing view of the backend policy already defined by:

- [FACTORY.md § The engine model](../../../FACTORY.md#the-engine-model-multi-project-2026-07-13):
  production roles use Codex with optional same-family Cursor OpenAI fallback;
  checking roles use Claude Code with optional same-family Cursor Anthropic
  fallback; selection occurs before task submission and is never a retry.
- [Operator runbook § Model provider down](../../../runbooks/operator.md#model-provider-down-claude-or-openai-outage)
  and [§ Preflight failed before launch](../../../runbooks/operator.md#preflight-failed-before-launch):
  operators need a non-task diagnostic that shows whether primaries and
  calibrated fallbacks are available before a run.
- [`scripts/lib/backend-policy.sh`](../../../scripts/lib/backend-policy.sh):
  the existing adapter/family map, `READY`/`UNAVAILABLE`/`INVALID`/`UNKNOWN`
  probe states, `fallback_disabled` reason, and fail-closed route resolver are
  authoritative. This ticket exposes them; it does not define a second policy.

## Frozen command contract — version 1

### Entrypoint and compatibility

Operator invocation, from the kit repository root:

```bash
scripts/adapters/contract-test.sh --readiness
```

`--readiness` takes no value and does not accept task text, a ticket ID, a role,
or an adapter list. It loads `FACTORY_GLOBAL_ENV` (default
`$HOME/.factory/global.env`) exactly as `contract-test.sh` does today and checks
these policy-owned adapters in this exact order:

1. `codex` — family `openai`
2. `cursor-openai` — family `openai`
3. `claude-code` — family `anthropic`
4. `cursor-anthropic` — family `anthropic`

The existing no-argument default, `--adapters <comma-list>`, and `--routes`
modes retain their current behavior. The usage line becomes:

```text
usage: contract-test.sh [--adapters a,b | --routes | --readiness]
```

### Probe and route semantics

Each adapter is evaluated through `factory_probe_adapter`; family names come
from `factory_adapter_family`. State and reason are printed verbatim from
`PROBE_STATE` and `PROBE_REASON`. In particular, an intentionally disabled
Cursor fallback is not relabeled: it is
`state=UNAVAILABLE reason=fallback_disabled`. That exact pair distinguishes
disabled optional fallback from unavailable authentication/executable/version
probes and from `INVALID` configuration.

After all four adapter records are printed, readiness is resolved for the two
role groups using the existing `factory_resolve_role` policy:

- `production` / `openai`: primary `codex`, fallback `cursor-openai`
- `checking` / `anthropic`: primary `claude-code`, fallback
  `cursor-anthropic`
- A ready primary is selected with reason `primary_ready`.
- Only primary state `UNAVAILABLE` may select a ready fallback; its reason is
  `primary_<primary PROBE_REASON>`.
- Primary state `INVALID` or `UNKNOWN` fails closed and never selects fallback.
- If no route is safe, `adapter=none` and the route reason is the resolver's
  `FACTORY_RESOLVE_ERROR` verbatim.

The command exits `0` only when both route records are `state=SAFE`; it exits
`1` when either route is `state=UNSAFE`. Command-line usage errors remain exit
`2`. The existing `timeout` and `python3` prerequisite checks remain in force;
a failed prerequisite also exits `1`.

### Output

There is no JSON mode. Standard output/error remains line-oriented with the
existing `[contract-test]` prefix. Adapter records come first in the order
above, followed by production then checking:

```text
[contract-test] adapter=<adapter> family=<family> state=<PROBE_STATE> reason=<PROBE_REASON>
[contract-test] route=<production|checking> family=<family> state=<SAFE|UNSAFE> adapter=<selected-adapter|none> reason=<selection-or-error-reason>
```

No model ID, version string, credential value, task text, or ticket content is
printed. Existing prerequisite and final success/failure lines may follow these
six records and retain their current wording; tests match the six records as
whole lines rather than treating the complete process output as an exact
six-line body.

## Ambiguity log

- **Which command should operators run?** Resolved from the existing adapter
  contract entrypoint and the runbook's current `--routes` advice: add an
  explicit `--readiness` mode to
  `scripts/adapters/contract-test.sh`, rather than adding another script.
- **Does disabled fallback make readiness fail?** Resolved from
  [FACTORY.md § The engine model](../../../FACTORY.md#the-engine-model-multi-project-2026-07-13)
  (“optional”) and current preflight behavior: disabled fallback is visible as
  `UNAVAILABLE/fallback_disabled`, but a ready primary keeps its route safe.
- **When may fallback be selected?** Resolved from
  [`factory_resolve_role`](../../../scripts/lib/backend-policy.sh): only an
  `UNAVAILABLE` primary can fall through; `INVALID` and `UNKNOWN` fail closed.
- **What does “no safe route” mean?** Resolved as either required role group
  being unsafe, because the documented factory requires both production and
  checking families to run the ticket lifecycle.
- **How is “never submits task content” observable?** Resolved from the existing
  stub trace contract in `ci/test-factory-scripts.sh`: all task-bearing stub
  branches append to `FACTORY_TEST_TRACE`, so an empty trace after every
  readiness fixture is the mechanical assertion.
- **Where is the command documented?** Resolved to `runbooks/operator.md`,
  already the operator-owned troubleshooting guide linked from the current
  contract-test advice. No operator decision was required.
