# T-102 — /health reports approvals summary

State: In progress
Branch: ticket/T-102-health-approvals-summary
Risk class: low (read-only endpoint, no external actions)

## Description

T-101 gave operators queue counts on `GET /health`. The other thing an operator checks at a glance is the approvals pipeline: how many proposed actions are waiting for a human, and how the closed ones ended. Extend `GET /health` to also report approvals counts by status.

The approval statuses in `conformance/app/server.js` are: `pending`, `sent`, `rejected`, `blocked_recipient`. The existing `ok` and `queue` fields must not change (T-101's tests stay green).

## Acceptance criteria (planner freezes the exact contract)

1. On a fresh server, `/health` reports zero approvals in every status. → satisfied when the response body matches Frozen contract §"Fresh server" exactly.
2. After a job completes and proposes an action, `/health` shows one pending approval. → satisfied when the response body matches Frozen contract §"One pending approval" exactly.
3. After that approval is approved, `/health` shows it under sent, and pending returns to zero. → satisfied when the response body matches Frozen contract §"Approved" exactly.

## Frozen contract

`GET /health` gains an `approvals` field alongside the existing `ok` and `queue` fields (unchanged, per T-101). Response is `200 OK`, `Content-Type: application/json`.

Shape:

```json
{
  "ok": true,
  "queue": { "pending": 0, "done": 0, "dead": 0 },
  "approvals": { "pending": 0, "sent": 0, "rejected": 0, "blocked_recipient": 0 }
}
```

- `approvals` has exactly these four keys, always present, in this order, values are non-negative integers counting `state.approvals` entries by `.status` (statuses defined in `conformance/app/server.js`: `pending`, `sent`, `rejected`, `blocked_recipient`).
- No other keys are added to `approvals`. No existing key of the top-level response (`ok`, `queue`) changes shape or meaning.

Acceptance criterion → exact expected body:

1. **Fresh server** (AC1) — no events posted yet:
   ```json
   { "ok": true, "queue": { "pending": 0, "done": 0, "dead": 0 }, "approvals": { "pending": 0, "sent": 0, "rejected": 0, "blocked_recipient": 0 } }
   ```

2. **One pending approval** (AC2) — after posting an event and waiting for its job to reach `done` (which produces one approval in `pending`):
   ```json
   { "ok": true, "queue": { "pending": 0, "done": 1, "dead": 0 }, "approvals": { "pending": 1, "sent": 0, "rejected": 0, "blocked_recipient": 0 } }
   ```

3. **Approved** (AC3) — after `POST /api/approvals/:id/approve` on that approval (recipient on allowlist, so it succeeds):
   ```json
   { "ok": true, "queue": { "pending": 0, "done": 1, "dead": 0 }, "approvals": { "pending": 0, "sent": 1, "rejected": 0, "blocked_recipient": 0 } }
   ```

If this contract proves wrong during build or test-authoring, the ticket goes back to Ready for re-planning as a new version — do not silently change the shape.
