# T-103 — rejections carry a reason

State: In progress
Branch: ticket/T-103-reject-reason
Risk class: low (approval lifecycle metadata, no external actions)

## Description

When an operator rejects a proposed action today (`POST /api/approvals/:id/reject`), the proposal just closes. In a real approval flow the *why* matters: audits and the proposing side both need it. Let rejections carry an optional reason.

- `POST /api/approvals/:id/reject` accepts an optional JSON body `{ "reason": "<string>" }`. The reason is stored on the approval record and survives restarts (persisted with the rest of the state).
- The approval as returned by `GET /api/state` exposes the reason on rejected approvals. Absent a reason, the field is present and null (planner freezes the exact representation).
- Rejecting an approval that is not `pending` must not change it and must be refused with a clear status code (planner freezes which).

## Acceptance criteria (planner freezes the exact contract)

1. Reject with a reason → the approval in `/api/state` is `rejected` and carries that exact reason string. → satisfied when the approval object matches Frozen contract §"Rejected with reason" exactly.
2. Reject without a body or without a reason → the approval is `rejected` with the frozen "no reason" representation. → satisfied when the approval object matches Frozen contract §"Rejected without reason" exactly.
3. Rejecting an already-rejected (or otherwise non-pending) approval → refused with the frozen status code (`409`) and the record is unchanged, including its original reason. → satisfied when the response matches Frozen contract §"Reject on non-pending" and a follow-up `/api/state` fetch shows the approval byte-for-byte unchanged from before the second reject call.
4. Reason survives a server kill and restart (persisted atomically like all other state). → satisfied when, after `SIGKILL` + restart, the approval object in `/api/state` still matches Frozen contract §"Rejected with reason" exactly (same pattern as `conformance.test.js` test 7).

## Frozen contract

### `POST /api/approvals/:id/reject`

Request body: optional JSON `{ "reason": "<string>" }` (`Content-Type: application/json`; a missing/empty body is legal, matching today's behavior).

- `reason` resolution: if the parsed body has a `reason` key whose value is a `string` (including `""`), that exact string is stored. In every other case — no body, no `reason` key, `reason: null`, or a non-string `reason` (number/object/array/bool) — the stored reason is `null`. No 400 is raised for a non-string `reason`; it is silently treated as absent. (Out of scope: this ticket does not add body-shape validation beyond this rule.)
- Unchanged from current behavior: unknown `:id` → `404 { "ok": false, "error": "no such approval" }`. Non-`pending` approval → `409 { "ok": false, "error": "already <status>" }`, and the approval record is not modified in any way (status, reason, or otherwise).
- On success (approval was `pending`): approval transitions to `rejected`, its `reason` is set per the resolution rule above, state is persisted. Response is `200`:
  ```json
  { "ok": true, "status": "rejected", "reason": "<string-or-null>" }
  ```

### `GET /api/state` — `approvals[]` shape

- Approval objects for status `pending`, `sent`, or `blocked_recipient` are **unchanged**: no `reason` key is added to them.
- An approval object gains a `reason` key **only when/if it is rejected**, at the moment of rejection, and never removed or changed afterward (a second reject call is refused per above, so once set it is immutable).
  - **Rejected with reason** — reject called with `{ "reason": "no longer needed" }`:
    ```json
    { "id": "appr-e1", "jobId": "job-e1", "action": { "...": "..." }, "status": "rejected", "proposedAt": "...", "reason": "no longer needed" }
    ```
  - **Rejected without reason** — reject called with no body, `{}`, or a non-string `reason`:
    ```json
    { "id": "appr-e1", "jobId": "job-e1", "action": { "...": "..." }, "status": "rejected", "proposedAt": "...", "reason": null }
    ```
  - **Reject on non-pending** — second reject call on either of the above returns `409 { "ok": false, "error": "already rejected" }`; the approval object retrieved from a subsequent `/api/state` call is identical (including `reason`) to what it was right after the first reject.

If this contract proves wrong during build or test-authoring, the ticket goes back to Ready for re-planning as a new version — do not silently change the shape.
