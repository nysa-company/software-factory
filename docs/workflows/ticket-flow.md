# Ticket workflow

The full lifecycle of one ticket, with the two invariants that never bend: **tests are authored before implementation by a different model family**, and **the operator approves from an evidence bundle before merge**.

## Sequence

1. **Operator** moves a ticket from Backlog to Ready by running `operator ready --ticket T-NNN`. For a `PREVIEW_PROVIDER=none` product, the operator first adds exact `Builder ownership: path[, path] only` naming every production file the ticket may create or modify. The receipt is projected into the ignored operator map; the dispatcher materializes it on the ticket branch and no live API call is made by preflight.
2. **Dispatcher** runs the existing provider-free ticket readiness contract before either shadow or claim succeeds. A refused ticket is named and skipped without a branch, cell, lease, model plan, route, or state mutation; eligible siblings continue, and correcting the protected ticket metadata makes it ordinarily admissible on the next scan. It then creates the exact clean ticket branch/worktree from current protected `origin/main` and runs trusted operator-field materialization to create and verify its remote ref. It invokes sealed `models pin`, which resolves the active profile (or default `cursor-opus-v2`) only if one ordered portfolio has ready candidates for all six roles with distinct production/checking families. The one pushed commit contains both `Kit-SHA` and `factory/route-plans/<ticket>.json`; preflight retains the same readiness recheck immediately before Planner.
3. **Planner** uses the exact production-lane route pinned for Planner, starts Planning, and posts the spec'd description, acceptance criteria, and frozen contract. If the product docs cannot answer a question, ticket → Blocked-Escalated with the question instead.
4. **Spec-linter** uses its pinned checking-lane route, remains in Planning, checks criteria quality, material contract coverage, consistency, trust-boundary edge coverage, protected-test source-boundary guards for every Builder-owned production file, and bounded static collisions between new global-shell text and page-wide protected text assertions. Provider-free readiness already rejects a tracked static SHA-256 guard over a Builder or Test-author path when its exact protected test is not an owned declared conflict. An undeclared, unowned, unknown, or unparsable static guard fails before Builder and names the exact protected test and assertion when known. It appends all findings plus one `SPEC-LINT: PASS`/`FAIL` verdict line. Non-blocking exhaustive-coverage recommendations use `SPEC-WARN:` and may accompany PASS; they proceed to Test-author without a Planner round. FAIL is reserved for a missing material decision, contradiction, weakened trust boundary, data-loss risk, or unintended external effect. FAIL sends only that ticket back to Planner. The transition receipt exposes the current failed lap; the third Planner/Spec-linter failure escalates before another role launch.
5. **Test-author** uses its pinned checking-lane route, starts Building, and commits failing tests as the first commits on the ticket branch, asserting the frozen contract. Confirms they fail for the right reason.
   A successful Planner run after any Test-author evidence opens a new test-first epoch: Spec-linter, Test-author, and Builder must all run again in that order. Earlier evidence remains immutable history but cannot satisfy the repaired contract.
6. **Builder** uses its pinned production-lane route in a fresh git worktree on the same branch and implements until tests, lint, and typecheck pass. Never touches test files — CI enforces this. Opens the PR.
7. **CI** runs: lint, typecheck, tests, build, self-referential snapshots, test-immutability check. The trusted ticket-PR helper compares GitHub's reported required checks with the complete app-bound required-check rules for protected `main`; before honoring an omitted or pending check wait, the controller refreshes a stale ticket branch against protected `main`, because GitHub cannot publish pull-request checks for a conflicting merge. A current-base omitted or pending check waits without launching a role. A PR-gated waiting ticket is reconsidered on the existing bounded reconciliation interval while a sibling worker remains live; it launches at most once and stale or failed head evidence stays closed. Completed failures are mandatory Reviewer evidence for a repair verdict.
8. **Reviewer** uses its pinned checking-lane route in Review and checks test adequacy, CI, and spec conformance. Approve, or name the exact Test-author/Builder repair owner and return only that ticket to Building. Any later Builder or Test-author run invalidates the approval and requires a fresh review. Reviewer has no semantic-round cap; ordinary ticket-budget admission decides whether another authenticated repair can launch.
9. **Narrator** starts only after the ticket-PR helper revalidates successful required checks and the exact current head against the latest successful Reviewer evidence. For the supported Railway publication contract, that helper also extracts only `railway-app`'s validated `*.up.railway.app` Web endpoints, verifies every deployment's exact head, runs any configured head-bound product preview preflight, and waits while required evidence is pending. A product may instead declare strict `NONVISUAL_PATHS`; only a complete exact-head PR file inventory confined to those paths plus current-ticket Factory metadata receives the trusted nonvisual marker, while every mixed or unsafe shape retains the deployment gate. The controller passes the exact PR, head, publication evidence, and protected-check result; the runner adds the effective accounting snapshot after reserving the current attempt. Narrator uses its pinned production-lane route, remains in Review, verifies the trusted behavior, captures required screenshots only for visual surfaces, and commits the bundle: plain-language summary, preview or explicit nonvisual N/A, screenshots or N/A, criteria table, risk line, cost, rollback note. It never reruns tests, builds, repository checks, secret scans, or a broad suite. A structurally invalid bundle with no bundle attestation authorizes one automatic Narrator correction; every later malformed result waits provider-free for an exact ticket-only authorization of the next Narrator round. An explicit `NOT APPROVABLE:` bundle instead routes directly to Builder without another Narrator launch, preserving the failed evidence until a changed deployed head is re-reviewed. Under contract 1.3, the dispatcher then invokes trusted `ticket-attest --action bundle`; it rejects an explicitly non-approvable bundle, verifies the exact reviewed SHA, every successful run's tuple against the committed six-role route plan, the route-plan blob/digest and policy hash, allowed post-review paths, bundle blob, and unique exact PR before committing Awaiting Approval. Contract 1.2 still stops in Review.
10. **Operator** moves Awaiting Approval → Approved by running `operator approve --ticket T-NNN` from a machine with the controller state dir. The receipt records the exact observation time and is projected into the operator map without changing the ticket checkout; the later approval attestation is its durable Git evidence. Trusted `ticket-attest --action approval` accepts only an approval receipt newer than the unchanged bundle attestation, commits Approved and its binding attestation, and requests ordinary protected GitHub auto-merge with the repository's exact configured method for the exact current PR head. A retry after receipt consumption but before overlay cleanup revalidates that exact attestation and merge request before clearing the unchanged overlay. A failed or unconfirmed request retains the overlay for a receipt-valid retry and never bypasses protection. If the exact PR instead becomes definitively red before approval, the existing authenticated publication-repair transaction withdraws the stale bundle and returns only the named Builder or Test-author repair to Building; no business approval is required for that repair.
11. After GitHub merges, the dispatcher prepares exact clean `chore/tNNN-closeout` with `HEAD == origin/main`. If the merge lands between the merged-state query and the open-PR lookup, the controller rechecks merged state once and enters this same closeout path instead of parking the ticket. Trusted `ticket-attest --action done` requires the merged PR head to be the approval receipt commit, validates protected bundle/approval blobs, and requires every configured exact post-merge context successful and unambiguous on the merge commit. It projects the ledger once, writes and pushes one Done closeout commit, creates or reuses the exact factory-owned metadata/accounting PR, and requests protected auto-merge with the configured method. Retries revalidate that exact commit and converge PR creation/auto-merge without another projection or commit. No second business approval is required.
12. Only after the closeout PR merges and the strengthened protected-main reader validates Done does `next-stage` return `COMPLETE`. The dispatcher then invokes trusted `release` with the matching opaque lease. There is no external witness for this projection — Done is Git- and receipt-only, verified by reading protected main and the ledger. At concurrency two, every attestation action receives the lease in memory; it is never released merely because a closeout PR exists.

Roles never re-resolve the portfolio. Before submission, the wrapper re-probes
only the role's exact pinned route. Once any task-bearing CLI starts, every
failure is terminal for that run; the dispatcher escalates instead of launching
another route.

Every mutating role must finish with a new commit and a clean ticket worktree;
the trusted wrapper non-force pushes that commit and verifies the remote tip.
Reviewer is read-only and must leave the branch, HEAD, and worktree unchanged.

## Failure routes

- Contract wrong mid-build → ticket back to Planning; planner re-plans; contract change is a new version, never a silent edit.
- Spec-lint or authenticated contract-repair reaches 3 failed laps → Blocked-Escalated before another role launch. The receipt-bound count and controller event name the loop, attempt, limit, and stopped stage. Reviewer repair remains uncapped and stops only at ordinary ticket-budget admission.
- Budget cap hit → the wrapper refuses to start (or the adapter's hard budget stop ends the run); whoever launched the run moves the ticket to Blocked-Escalated with the wrapper's message. At pilot stage that's the operator; a dispatcher automates it later.
- Confirmed temporary credit exhaustion → operator may add a TTL-bound `credits_exhausted` override for the narrow account-route, family, model, or route scope, then pin a new ticket. Existing ticket plans do not change. Subscription quota telemetry is incomplete and cannot safely automate this judgment.
- Preview deploy broken → Narrator records a non-approvable result and no bundle attestation is created. After the preview is repaired, the sequencer permits one Narrator retry; a second invalid bundle escalates.
- Defect found after Done → new bug ticket linked to the original (escaped defect); one reopen allowed, second → Blocked-Escalated.
- Controller state dir unavailable → in-flight execution continues from Markdown; new priority, Ready, approval, or unblock actions wait until a machine with the state dir can issue the operator receipt.

## Branch mechanics

- Branch per ticket: exactly `<TICKET_BRANCH_PREFIX><T-NNN>` (default `ticket/T-NNN`), with no slug or suffix.
- Commit order is load-bearing: test commits (author: test-author) first, implementation commits (author: builder) after. The reviewer verifies authorship; CI verifies the builder's commits touch no test paths.
- One PR per ticket. The single business approval is the operator receipt-bound bundle approval; it enables protected auto-merge without bypassing required checks or conflicts. No direct pushes to main.
